建议把试点做成一个**带权限控制、能回到原文核验的科研资料检索与问答助手**：复用现有 Python 服务、PostgreSQL 和文件存储，使用固定的“检索证据 → 必要时归纳 → 校验引用 → 返回”流程。两个人、八周内，优先证明用户能找到可信资料、每项关键回答有据可查，以及内部笔记不会越权泄露。当前没有证据支持同时引入 Kubernetes、图数据库、多 Agent 和复杂事件总线。

这里的“当前”仅指你提供的系统情况，未经过独立检查。资料数量、语言、扫描件比例、服务器配置、模型资源、预算和峰值流量都未知，不能据此承诺容量。下面给出可执行的试点方案；其中数字是建议验收目标，均不是实测结果。

试点先限定为：公开论文与已明确授权范围的教师笔记，支持资料搜索、原文摘录和有证据的简短归纳；不承担自动执行科研任务、开放网络研究或复杂自主协作。内部笔记的“教师授权”还需落实为哪些人可访问、可否用于模型处理、可否离开校内环境。公开可访问的论文，也应确认允许采用的全文处理范围。模型端点与费用未给出，第一周须锁定一个允许处理相应资料且预算可承受的端点；若暂时没有合适端点，先交付搜索、摘录和引用，明确告知归纳功能尚未开放，内部笔记不能因此被默认送往外部模型。

现有 Python 服务继续作为唯一查询入口。同一代码库增加资料导入、检索、引用组装和模型调用模块；导入由一个独立后台进程执行，避免 PDF 解析挤占交互请求。PostgreSQL 保存文档元数据、访问范围、文本片段、索引状态、导入任务及必要审计记录；文件存储保留原始文件及明确版本。先部署在现有可管理的环境中，给查询和导入设置资源与并发上限。第一周要确认备份、身份接入和服务恢复的实际责任，两个人中均需有人能够按操作说明恢复服务。

先用现有检索能力及 PostgreSQL 中的文本、元数据索引建立基线。中文分词、缩写、英文术语和作者名必须拿真实查询验证，不能假设默认配置就能覆盖校园资料。如果同义表达导致相关证据持续漏召回，再在第二至三周增加一条向量召回分路：向量检索是把查询和文本映射到可比较的表示，以补足词面不重合的情况；它不能保证事实正确，也不能替代权限过滤。优先检验现有数据库能否以可维护的扩展或受限实现满足需求，通过同一评测集证明增益后才纳入当前版本。不要在尚未知道语料规模和漏召回原因前另建一套向量基础设施。

端到端流程需要闭合到以下程度：

1. **资料进入系统。** 导入者登记来源、授权对象和负责人；为每个文档建立 `source_id`，用内容哈希区分版本。解析结果保留页码、章节、段落或原文位置，文本片段携带文档版本与定位信息。扫描件或解析失败的文档进入待处理状态，不能悄悄作为完整资料发布。后台任务按“文档版本＋处理配置版本”去重，记录待处理、处理中、可用和失败状态，使用有时限的任务占用与有限重试；只有文本、定位和索引均就绪才发布为可查询版本。重复导入不能重复生成资料，进程中断后能够恢复。

2. **确定用户能看什么。** 身份认证取得用户与所属群组，服务端根据当前授权计算可访问文档集合。查询条件把访问范围带入每一条召回分路，在读取正文、构造模型上下文前完成授权；不能先检索全部资料再让模型判断权限。原文下载和引用打开接口也重新鉴权。资料内的指令只作为待分析内容，不允许改变权限或触发工具调用。

3. **检索可用证据。** 对问题做有限的文本归一化，按正文、标题、作者和日期检索；在已授权范围内返回候选片段，再去重并限制数量与总长度。可从最多约八个片段开始调参，这只是起点。若引入向量分路，按候选排名合并，并用相关性样例验证；不能把两种原始分数直接当作同一尺度。检索结果保留稳定的证据编号、版本和出处。证据为空时返回“在当前可访问资料中未找到足够证据”，不让模型补出一个貌似完整的科研结论。

4. **受约束地归纳。** 默认每个问题至多一次生成调用，输入只有必要证据，并要求回答中的重要事实关联给定证据编号。区分论文结论与教师个人笔记；来源互相冲突时并列说明及引用，避免自动合成为确定结论。仅跨两份文档归纳，并不需要两个 Agent；一个固定流程可以先取齐资料，再统一回答。特别长或无法在当前上下文覆盖的问题，应缩小问题或返回相关资料清单。

5. **校验并交付。** 服务检查引用编号是否来自本次证据集合、对应版本与原文定位是否有效，再组装标题、作者/来源、年份、页码或段落及可访问链接。对准备交付的内部证据再检查当前授权，处理生成期间发生的撤权。格式校验只能证明“引用存在”，不能证明“原文支持该结论”；后者必须进入人工评测，首版尽量使用短答案和可核验摘录。引用缺失、格式异常或生成超时时，退回原文证据列表，不把生成失败包装成已回答。

资料撤权或版本更新也属于这条链路。数据库保存当前可用版本与授权状态，撤权立即阻断检索、答案交付和原文访问，后台再清理旧索引及派生内容；不能等缓存自然过期。若后续引入缓存，键与有效性至少关联访问范围、权限版本、文档/索引版本和生成配置；每次命中仍校验当前访问权限。首版可以先不缓存完整答案，以减少跨用户泄露与失效管理成本。

查询入口设置每用户限流、总并发上限、有限长度和总超时，后台导入设独立限额。模型限流或不可用时直接显示证据检索结果；在同一超时预算内才考虑有限重试。日志记录请求编号、分段耗时、证据编号和版本、错误类型、模型用量，避免默认记录完整内部笔记或所有问题正文；保留期由校内使用要求确定。权限判断由服务代码负责，提示词里的“不要泄露”只作补充。

为什么暂不采用团队提出的四项技术，以及何时值得改变判断：

| 技术 | 此时的判断与原因 | 重新考虑需要什么证据 |
|---|---|---|
| Kubernetes | 暂缓自建集群。它解决部署、调度和多副本管理问题，本身不能消除慢 SQL、模型排队或模型配额限制。维护集群会占用两人的交付时间。 | 校园已有成熟托管平台、接入成本低时可直接复用；或实测需要多实例与故障恢复，而现有部署方式无法可靠维护。 |
| 图数据库 | 暂缓。资料检索和引用定位可先用现有存储完成，作者、论文等少量关系也可先用关系表表达。 | 核心问题确实要求多跳关系查询，现有 SQL/检索难以满足，且已有可持续维护的实体、关系与来源数据；须用实际问题对比正确性与成本。 |
| 多 Agent | 暂缓。当前是只读资料问答，固定流程可控制权限、调用次数和引用。额外协作会增加调用量、状态与失败分支。 | 存在可独立执行的复杂子任务，固定流程持续失败，且受控对照证明多 Agent 的端到端质量收益足以抵偿延迟、费用及运维成本。 |
| 复杂事件总线 | 暂缓。导入与重建索引先用数据库任务表加一个后台进程，任务去重、占用超时和重试状态必须完整。 | 多个独立消费者需要订阅与重放事件、任务积压或交付语义已超出现有方案能力；先确认普通任务队列能否解决，再考虑事件总线。 |

这些判断针对当前约束，不是“越简单越好”的通则。权限、稳定引用和可恢复导入即使增加工作量也必须做；没有对应问题的组件才应暂缓。

两人的八周安排可以这样落地，默认两人都能参与开发与互相审查，不额外假设有专职平台或测试团队：

| 时间 | 工程师 A 主要负责 | 工程师 B 主要负责 | 阶段交付与门槛 |
|---|---|---|---|
| 第 1 周 | 现有 API、身份、资源和耗时基线；确认模型与预算边界 | 资料抽样、授权与解析检查；建立评测题及证据标注 | 跑通最小资料查询与原文定位；确认范围、目标和未知项。若模型不具备合适处理条件，锁定检索试点范围。 |
| 第 2—3 周 | 查询、权限、引用打开接口及必要的归纳调用 | 版本化导入、任务恢复、检索基线；按误差决定是否补向量召回 | 完成少量授权资料的贯通链路，内部试用；引用与权限问题优先解决。 |
| 第 4—5 周 | 超时、并发、分段监控、降级与最小结果界面 | 修复解析/召回/引用错误，扩充覆盖资料和回归样例 | 锁定功能范围，以证据评测和完整请求测试收敛质量、延迟及调用成本。 |
| 第 6 周 | 代表性负载、限流、故障恢复及回滚演练 | 权限攻击样例、版本切换、撤权、错误与拒答回归 | 完成上线前门槛检查；未达标则修复或缩小试点。 |
| 第 7—8 周 | 逐批开放、观察峰值与错误、修复阻断问题 | 跟踪用户任务是否完成、复核引用、整理使用说明 | 在约定用户范围内验收，交付配置、数据/索引版本、评测记录、恢复说明及已知限制。 |

双方交叉审查权限与引用链路，并共同完成恢复演练。导入页面、界面美化和高级对话能力排在核心链路之后。计划应留下修复时间；八周最多只有十六人周，不能把所有时间都分配给新功能。

验证要分别回答“找到了证据吗”“证据支持回答吗”“用户看得到这些证据吗”“在实际负载下是否及时返回”，不能用一个总准确率替代。

建议第一周准备约 80 道代表性问题：40 道普通资料查询、15 道跨文档问题、10 道库内无答案问题、5 道矛盾或版本问题、10 道越权与恶意资料用例。每题标注权限主体、可接受证据及必要回答要点，至少留 30 题作最终独立于调参的留出集，分组报告结果。两名工程师可交叉检查原文支持性，学科结论的专业判定超出两人能力时，记录待教师确认，不能把“有引用”当作科研结论已获专业验证。

可采用以下建议门槛，第一周与试点使用者确认后冻结口径：

- 在有可用答案的题中，前八个候选覆盖必要证据的比例达到约 90%；跨文档题需覆盖所有必要来源，不能只召回一段就算成功。
- 人工逐项核对重要事实，至少 95% 有所引原文支持；实际生成答案的引用完整性也至少 95%。输出原文定位、版本与文档映射须全部正确。报告分子、分母与失败案例，不能只给四舍五入后的百分数。
- 无答案题不得用库外常识填成资料结论；对无依据的确定性回答设为阻断缺陷并复测。测试中的越权内容、撤权后内容泄露为零，是上线硬门槛；这仅描述已测样例，不代表证明所有攻击都安全。
- 在约定的代表性峰值与输入长度下，建议“证据结果”端到端 P95 不超过 2 秒，“完整归纳答案”P95 不超过 12 秒，20 秒总截止时间内返回答案或明确降级结果。在有足够证据且本应提供归纳的有效请求中，成功返回完整答案的比例建议至少 95%；超时降级不计为归纳成功，权限拒绝与无证据拒答单独计数。记录从收到请求到完整返回的时间，另记首个 token 时间，不能用流式首字速度替代完整回答速度。
- 记录每个成功问题的模型调用数、输入/输出量与费用；费用上限须依实际预算确定。对模型超时、进程重启、重复导入、解析失败、存储不可用、数据库恢复和版本回滚逐项演练，确认失败可见、资料可恢复且权限不丢失。

负载测试使用真实资料分布和脱敏后的代表性问题，记录硬件、部署配置、数据规模、索引与模型版本。先测分段基线，再做逐级并发、突发与持续负载，并在实测峰值的适当余量下复验。短提示、热缓存与空数据库上的测试不能证明真实问答容量。一次修改只比较相关指标，并用固定问题回放，避免把更换问题集造成的变化当成优化收益。

对于三周后增长到 5000 人且实测变慢，首先重新评估的是**实际负载与瓶颈假设**，而不是按用户数整体换栈。

初始 300 次/日的全天平均是 `300 ÷ 86400 ≈ 0.0035 次/秒`。只有在每用户使用强度等条件保持不变的假设下，用户数从 200 到 5000 才对应约 7500 次/日，即全天平均约 `0.087 次/秒`，或平均分布在八小时内约 `0.26 次/秒`。这些都不是峰值，不能据此宣布单机够用或不够用。应重新测量活跃用户、每人问题数、上课或作业时段突发、同时在途请求、问题长度、每题证据量和生成长度。人数增加也可能伴随更多资料、权限群组与不同任务分布，因此旧评测集的代表性也需复查。

保留同一完整请求口径，将耗时拆成入口等待、权限查询、检索、文件读取、模型等待/生成和响应返回，并按忙闲时段、长短问题、缓存命中及资料类型切片。下面是待验证的竞争假设，不是已经确认的根因：

| 观察或假设 | 最小区分证据 | 优先尝试及后续条件 |
|---|---|---|
| 请求进入服务后排队，CPU/内存或并发资源饱和 | 等待时间与资源曲线同升；去掉模型调用后仍复现 | 隔离导入任务、修复阻塞、调节工作进程和连接池；确有 CPU 容量瓶颈时增加实例。若模型等待主导、服务资源空闲，此假设不足以解释延迟。 |
| SQL/检索变慢 | 同一查询回放，检查查询计划、过滤后候选数、连接池等待与检索分段耗时 | 修索引、查询和权限过滤路径，减少无效候选；若数据库段始终稳定，不能把根因归给 PostgreSQL。 |
| 模型限流、排队或生成过长 | 检索耗时稳定，模型段尾延迟/限流随并发或 token 数增加；短上下文对照明显改善 | 缩短上下文与答案、限并发、调整获准端点的容量/配额或模型；若模型段稳定，则转查其他链路。Kubernetes 不能解除外部模型配额。 |
| 文档增多或检索质量下降，使证据量和补救调用增加 | 统计每题候选/上下文长度与调用数，固定旧语料回放并对比新语料切片 | 修解析、切片与召回，必要时引入已经验证有效的向量分路；不能先用更多 Agent 掩盖证据缺口。 |
| 网络或文件读取成为瓶颈 | 记录存储/网络耗时，同一资料本地与完整链路对照 | 减少重复读取、优化连接及可安全复用的数据；若实际 I/O 耗时不变，继续查其他假设。 |

先用限流、并发上限和证据列表降级控制排队，同时保留诊断日志。每项改动在同一负载与问题分布下比较完整 P95、失败率、引用质量和成本。若容量仍不足，限制试点准入或暂时降低归纳功能覆盖范围，不以放松权限、删除引用或不受控重试换取表面速度。

此时还应重算三项决定：现有部署是否需要多个查询实例；数据库和模型是否存在不可通过局部修复解决的容量限制；剩余五周的功能与性能修复安排。增长可能使部署自动化或普通任务队列变得值得投入，但图数据库取决于关系查询需求，多 Agent 取决于复杂任务的质量收益，事件总线取决于独立消费者与交付语义，三者都不会因“5000 人”自动成为正确答案。如果校园已有可用的托管 Kubernetes，重新核算接入成本也可能改变最初判断。

若第三周已经出现真实用户延迟问题，第 4—5 周应优先用于分段诊断与容量修复，暂缓高级功能；范围变化、触发数据、对照结果和回滚方式写入简短决策记录。核心验收仍是授权范围内的资料可查、结论有据、性能达标、失败可恢复。本文没有接入或检查你的服务、资料和模型，没有运行压测或验证上述阈值；落地前须用第一周基线和后续实测替换这些假设与目标。
