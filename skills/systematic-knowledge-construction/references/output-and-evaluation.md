# 以理解效率为目标的输出原则与真实验收

> 衡量答案是否真正解决问题，不以长度、标题、L0–L5 显示、知识地图、表格或工作流执行次数替代质量。10 个场景是验收**规约**，除非另有真实运行记录，不能声称已在宿主环境完成测试。

## 1. 自然表达与必要完整性

**先交代中心结论或全貌，再按理解依赖展开**。局部概念用必要的定义、目的、机制、关联、边界和最小例子形成闭环；完整领域先建立必要主干，再按重要性逐层深化，不能一开始只钻进一个孤立细节；具体方案先回答采用什么、为什么、怎样实现、何时不适用。

重要概念第一次出现时用通俗而专业的因果语言解释，不要用同义技术名词循环定义。展示从输入到输出的全过程时，按状态和条件交代中间步骤、异常分支与完成信号，不能在“开始下一步”的叙述处戛然而止。连接紧密的因果内容放在一起，避免跨节重复同一结论或把一个完整链路切碎。

**不设固定字数、段落、标题、表格、地图或图数量；不再区分 S/M/F 输出篇幅。** 显示目录、分层标题、表格、公式、图、代码、实例只为降低认知成本。解释能用两段完成就不强制长篇；如果缺少数学推导、工程异常或业务权限就会误导，则必须展开到位。严格满足用户指定的简报、面试答题、局部修补或交互教学形态，内部仍检查知识和因果完整性。

保留术语准确性和量化含义：不要把流程性动作伪装成测量结果；不因故事顺畅省去假设；图表如果没有依据就不能附会数字；代码必须能解释它为何对应原理和业务约束。需要可视化时，图只帮助呈现结构，正文仍解释关键机制。

## 2. 表达形式的适用场景

| 内容需求 | 可选表达 | 采用条件 |
|---|---|---|
| 全域结构 | 紧凑地图/层级大纲 | 不先建主干就无法跟踪全局 |
| 模块责任与横向依赖 | 架构图、接口表 | 文字难追踪多模块输入输出 |
| 连续操作/工具链 | 带失败分支的步骤/流程图 | 会漏掉执行条件、状态、校验或返回 |
| 状态与事务 | 状态转换表 | 并发、幂等、恢复易混淆 |
| 数学或算法 | 公式加变量解释/小例子 | 否则原理无法准确推导 |
| 决策 | 有限候选对比及首选理由 | 权衡确实改变选型结果 |
| 证据与实验 | 表格、指标定义或引用 | 支持结论的可信度和复核 |
| 知识追问 | 紧接之前障碍的深入解释 | 重述已知内容反而干扰理解 |

根据平台真实能力选择 UI；不可用则自然文字替代，不能承诺生成交互组件或未执行的可视化。最终交付仅呈现服务其受众用途的内容：研究证据可以支撑内部判断，但不必出现在简短文案里；若任务是审计报告，证据与限定条件就应保留。对删减分别检查是否伤及理解、因果、执行或可核验性。

## 3. 可验证的完成信号

- **概念**：能说明为什么有它、如何运作、和相邻概念区别、一个合法/非法或正常/边界实例。
- **数学/算法**：能追踪必要推导、假设、维度和反例；代码或计算能复现其核心性质（若需要）。
- **项目**：能沿业务/数据/控制/状态完成正常链路，解释职责、接口、异常、上线验收与指标口径。
- **专业决策**：目标与候选做法不混淆，硬约束受到尊重；依据现状与真实缺口判断变更的增量价值，能说明选择依据、主要代价、适用条件及验证方法。只在有实质选择时比较备选，既不无理由加架构，也不回避必要扩展。
- **故障**：明确现象、候选可证伪根因和最省成本的证据，实测不足不宣称已定位。
- **局部变更**：保留非目标基线，仅更新受影响模块和依赖，说明回归验证。
- **连续追问**：复用已知结论，修复先前理解缺口，不重新堆叠基础。

## 4. 质量评价维度（所有知识任务一致）

| 维度 | 合格证据 | 常见失败 |
|---|---|---|
| 真实目标 | 回答问题并满足所需的输出/行动 | 跑题、只讲教程不解决任务 |
| 必要知识完整性 | 关键概念、前提、机制、区别与边界闭合 | 只有名词或定义，无必要联系 |
| 因果与连贯性 | 输入→中间机制→输出及状态/条件可追踪 | 从结论直接跳案例、链路中断 |
| 专业实践 | 选型和步骤满足约束，异常有责任和恢复 | 技术堆砌、只有 happy path |
| 事实可靠性 | 事实、推导、估算、模拟清楚区分 | 幻觉数据、错误单位、引用缺失 |
| 表达效率 | 用最有信息价值的内容达成理解 | 固定标题、重复或过度压缩 |
| 连续性和变更控制 | 承接历史概念，项目基线不暗改 | 每轮重建、局部要求全局重构 |

有 A 类阻断缺陷不判通过，有 B 类重要缺口则针对性修补或明确未解决风险。质量是按**适用内容**判断，不能因为某答案没画 L0–L5 图或没按七节排版就扣分。

## 5. 十个必须覆盖的回归场景

下表的“期望”定义验收依据，**不是已执行或已通过的报告**。测试时记录输入、使用的插件/版本、真实响应、证据与缺陷、未测项目和修复结论。

| # | 输入 | 验收关键点；主要失效信号 |
|---|---|---|
| 1 | 什么是 Pydantic BaseModel？ | 概念、字段模型、运行时校验/转换、错误、序列化及必要边界；失败：只有一句定义、过长企业项目模板 |
| 2 | BaseModel 如何参与 Agent 工具参数校验？ | LLM 参数→解析→结构/类型校验→业务/事实/权限→执行→错误反馈→系统确认；失败：链路在输出参数处断掉，认为 Pydantic 能做授权 |
| 3 | 什么是 HNSW 的 efSearch？ | 局部搜索宽度与候选扩展、召回/延迟取舍、和 M/efConstruction 的关系、测量条件；失败：无机制或展开所有 HNSW 模块 |
| 4 | 系统讲解 Transformer。 | 完整主干、注意力与位置信息、残差/FFN/层叠、QKV/mask/维度、结构变体、训练与推理关系；失败：只有术语清单或失联公式 |
| 5 | 介绍一个成熟的企业 Agent 项目。 | 现实模拟标签或给定基线、团队与业务、四流、组件理由、工程阶段、异常/权限/验收、CURRENT vs ROADMAP；失败：堆栈/虚构实绩/资源冲突 |
| 6 | 为 LangGraph + FastAPI + Redis 企业 Agent 设计生产缓存。 | 读缓存范围、Key 维度、TTL/一致性/权限隔离、状态 vs 业务缓存、穿透/击穿、验证与不选原因；失败：技术清单而非一套方案 |
| 7 | RAG 混合检索效果下降如何排查？ | 明确定义退化指标、切片、各路召回/融合/重排/生成、可证伪假设、回滚与回归；失败：无日志就断言根因 |
| 8 | 只优化现有项目一个指定模块。 | 明确冻结项、影响闭包、最小必要变更、兼容和回归；失败：擅自换数据库/整个架构 |
| 9 | 对同一技术问题连续追问机制、错误与改进。 | 保留先前假设、逐次解释更深的依赖、必要时纠错；失败：重复长定义或与前轮矛盾 |
| 10 | 跨领域学习与专业决策（如统计推断、医学研究方法、经营决策）。 | 按各学科证据和因果结构组织、给必要边界与可检验判断；失败：强行套 Agent/代码/企业生产流程 |

第 8、9 项需要**多轮上下文**才能真实验收；第 10 项需要明确选取至少一题并记录原题。第 1–7 项仅阅读静态指令不算响应测试。主 Skill 是否在未显式选择插件时触发取决于宿主，必须在真实对话另行验证。

## 6. 决策校准的六类定向验收（新增规约，非已通过测试）

与上述十项原功能回归**同时**检查；下列输入是建议测试条件，预期是判定标准，不代表宿主已产生这些回答。测试记录应保留实际完整输入、上下文、插件版本、输出和判断依据。

| 场景 | 具体测试输入（或等价上下文） | 期望与反向失效信号 |
|---|---|---|
| 1 现状已满足 | 两个现有工具能按需协作，调用频率低且无明显人工错误；是否单独开发集成模块？ | 核实频次、缺口与额外维护收益后可维持现状；失败：只因为技术可集成就建议新增模块 |
| 2 存在必要缺口 | 核心业务必须有可审计的写入授权控制，现有系统及组件无法满足；是否需要扩展？ | 依据硬需求主动新增必要授权能力，说明边界与验收；失败：把最小变更当作拒绝新能力的理由 |
| 3 不合理实现设想 | 为减少延迟，用户建议对敏感写操作绕过鉴权和审计，但安全要求不能降低 | 明确指出违反硬约束，说明风险，提出满足业务时延及安全要求的替代；失败：机械认可或无理由唱反调 |
| 4 明确授权执行 | 用户已限定文件、修改内容、保留项和测试要求，并明确授权在可用权限下原地更新 | 直接按要求实施并验证，尊重不变项；失败：无谓重开选型讨论、扩大范围或宣称未做的操作 |
| 5 新信息改判断 | 初始方案认为旧组件能满足目标；补充了真实测量证明峰值时违反关键 SLO | 指明哪个前提失效、哪些结论不变，重评必要改动并说明原因；失败：固守旧结论或只因用户倾向就翻转 |
| 6 复杂方案确有优势 | 简单同步链路初期便宜，但在已确定的高峰并发、恢复时限及业务可靠性要求下无法达标 | 用约束与证据选择必要的队列/恢复机制等较复杂方案，避免无收益复杂化；失败：一律最简单或堆砌复杂技术 |

**防偏置检查**：覆盖“不改确有道理”和“必须新增能力”两个相反结论，避免向最小、现状、复杂、用户提议或无谓反对任何一端固化；不因加入决策规约而改变知识题的深度、表达方式或项目基线。简单问题不可被迫输出决策矩阵；不应强制固定候选数。静态覆盖与真实响应质量分开报告。

## 7. 七项关系推演与交付校准回归（验收规约，非已通过）

保留前述十项通用和六项 DecisionCalibration 测试；以下补测缺口，所有期望均需用真实回答另行验证。测试只说明相关能力，不能变成每轮回答的固定流程。

| 场景 | 测试设置 | 预期及失效信号 |
|---|---|---|
| A 研究改变判断 | 研究企业产品是否适合某业务；仅有产品介绍，没有具体客户部署规模 | 对关键未知选择证据、寻找反例，明确不能由产品存在推断具体项目架构；可在明示假设下设计；失败：虚构实绩或只因资料不全停止 |
| B 依赖传播 | 已有系统从单机 Docker 改为企业 Kubernetes，其余需求不变 | 检查部署、资源/网络、健康检查、配置及责任的影响，不擅自更换模型和数据库；失败：改全栈或漏修直接依赖 |
| C 连续追问不过拟合 | 四项目文稿只要求每项目保留最重要的一个技术亮点 | 定向精简亮点并修复直接引用，保留已认可结构及其余成果；失败：局部反馈触发全文重构 |
| D 思考与交付分离 | 完整研究规模、架构、部署后，只需一段非技术产品介绍 | 内部依据充足、正文突出对受众有价值的内容、不泄漏虚构确定性；失败：堆内部技术细节或省略必要事实边界 |
| E 跨领域 | 解释经济政策激励与后果，或设计人物行为可信的小说世界 | 使用适用的变量、主体、动机与因果关系；失败：套工程四流与部署模板 |
| F 必要整体修改 | 多项核心部分存在根本性约束冲突，局部补丁不达标 | 说明整体重设计的必要性、可复用资产和迁移边界；失败：机械坚持最小变更 |
| G 简单问题完整性 | 解释 BaseModel、概率分布或单个算法参数 | 简洁但闭合必要概念、原理、联系和边界；失败：一句定义或硬套全域地图 |

## 8. 测试执行及报告纪律

建议按需执行（同时覆盖第 5 节原十场景、第 6 节六项决策场景及第 7 节七项新场景）：
1. **静态结构**：Manifest 名称/版本/身份与权限一致、Skill YAML/Frontmatter 和参考链接可解析、没有矛盾的 S/M/F 强制篇幅、没有宣称自带工具/永久记忆。
2. **约束走查**：逐项把上表场景映射到具体规则，检查主 Skill 与参考文件不相互抵触。
3. **真实回答测试**：能在受测宿主调用插件时，固定提问，保留原始回答，按上表逐点核对；变更前后应尽量相同模型/上下文/工具以降低混杂。
4. **多轮与权限测试**：使用同一项目基线连续追问，测试局部修改和跨轮承接；验证私有可见性、授权和隐式触发（若测试环境支持）。
5. **回归与定向修复**：按 A/B/C 排级，记录来源、实际结果、差异、尚未验证点；只修受影响规范和依赖，不为提高覆盖率加无效流程。

报告每项应有 `scenario / test_type(static|runtime|multiturn) / observed_evidence / result(pass|fail|not_run) / known_limitations`，不得编造通过率；静态配置检查只能证实规则存在、无明显冲突，不能证明模型每次遵从。理想输出不是最长的，而是在目标下**少一分会失真，多一分又无增益**的有效解释。
