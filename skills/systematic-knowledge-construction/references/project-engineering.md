# 现实约束下的专业项目重建、实施与稳定演进

> 用于项目理解、工程设计、模拟业务场景、系统改造与技术决策。只有在任务涉及具体系统时应用；抽象理论与非工程学科不强行企业项目化。

## 1. 先明确任务类型与事实责任

**解释现有项目**：用户资料与现有基线优先，未给出的参数和实际成果不擅自补成事实。**设计新系统**：在明确约束下选择可执行首选方案。**教学模拟项目**：允许补足合理的假设，但每项规模、预算、周期、版本和成果保留“模拟/目标/估算/已测”标签。**局部优化**：明确指定变更与它的依赖闭包，其余基线不动。

`ProjectBaseline` 需要时覆盖：

| 维度 | 要记录的约束 |
|---|---|
| 业务与范围 | 用户场景、痛点、现有系统、输入/输出、功能边界与非目标 |
| 使用规模 | 总用户、活跃用户、请求峰值、业务读写比例、数据量及增长 |
| 团队与责任 | 人员数量、职能、本人实际负责模块、协作与审批边界 |
| 资源与周期 | 人月、交付阶段、预算、模型/GPU/存储/网络/已有服务 |
| 质量约束 | 准确率口径、SLO、P95、容量、安全、审计、隐私、合规 |
| 结构与契约 | 组件版本、协议、数据模型、API/Schema、失败与补偿 |
| 交付判据 | 评估样本、阶段验收、灰度策略、告警和回滚门槛 |

保持 `BaselineVersion` 和假设清单。四种状态不可混淆：`CURRENT`（有依据的已实现/当前设计）/ `LIMITATION`（已知缺陷和风险控制）/ `ROADMAP`（未来可选优化）/ `REDESIGN`（备选全局重做）。用户未证实的 CURRENT 应改用“用户描述的当前状态”，不要自动认作经独立测试。

## 2. 从需求到架构：每个组件都有理由

沿 `业务目标 → 可验收需求 → 核心链路 → 非功能约束 → 候选机制 → 组件选择 → 接口与状态 → 异常与测试` 做推导，不因为流行技术就堆栈。

重点讲清**原理如何改变工程选择**。例如：写操作有副作用，所以需要授权、确认、幂等及返回值验证；重试可能产生重复执行，所以必须结合幂等或先查询状态；LLM 输出结构化参数仍不保证业务事实为真，因此校验分结构/类型、语义/业务、权限/事实；RAG 受版本和权限约束，所以召回与证据引用必须携带文档版本及可见范围。

存在实质选型时，可记录简短 ADR：需求/硬约束、当前能力与目标缺口、真实可行的候选（适用时包括维持现状、已有能力复用或局部修改）、选择及不选的理由、增量收益与代价、切换条件和验证。无需凑固定方案数量；明确合理的已授权变更可直接推进。只批准**一套约束驱动的当前实现**，其余作为比较而非同时加到架构。已有基础设施可复用时核算实际收益与限制，但不因已有而排斥必要新能力。核对技术发布日期、当期版本能力、企业现有运行环境（如编排平台、数据库、网络与部署规范）、业务规模、团队职责、预算和时间线是否彼此一致；公开产品能力不能直接证明特定项目实际采用。技术名词必须对应所需功能与真实运维责任，整个端到端链路须在资源、权限、状态一致性和异常条件下成立。明确哪些属于行业通用原理，哪些只适用于该项目的假设。

## 3. 四条流与工程组件责任

完整项目应让读者能够追踪：
1. **业务流**：用户请求 → 身份和业务上下文 → 决策/查询/办理 → 系统确认结果 → 失败或人工接管。
2. **数据流**：源数据 → 清洗/版本/主键与权限 → 存储/检索/缓存/转换 → 服务消费 → 写回和审计。区分业务真源、模型生成、缓存和临时状态。
3. **控制流**：入口鉴权、路由、条件分支、HITL 确认、权限网关、工具/外部依赖执行、超时/有限重试/降级。
4. **状态流**：对话上下文、工作流检查点、业务事务、缓存和异步任务的各自所有权、持久化、并发与恢复边界。

对于每个关键模块交代 `位置 → 为什么需要 → 输入/输出/Schema → 上下游接口 → 执行与状态规则 → 失败/恢复 → 观测指标`。跨模块身份透传、权限、版本、缓存一致性、审计和幂等必须落实责任方；不能只在图上出现不进入流程。

## 4. 真实岗位交付：不是只有架构图

| 阶段 | 典型可核成果 | 协作者 | 完成证据 |
|---|---|---|---|
| 调研与需求 | 场景/用户故事、数据流、读写边界、风险、验收定义 | 产品、业务、安全 | 走查和需求确认 |
| 可行性与选型 | 关键链路 PoC、成本/性能/质量基线、ADR | 算法、平台、基础设施 | 可复现对照结果 |
| 设计 | API Schema、数据库/状态机、权限、幂等、错误契约 | 前后端、DBA、测试 | 设计评审与接口契约 |
| 开发 | 单元测试、边界检查、模块实现、监控埋点 | 研发与测试 | CI、代码审查与测试 |
| 联调 | mock/真实依赖、错误注入、权限/超时/回滚测试 | 上下游、QA | E2E 与业务验收记录 |
| 发布 | 灰度、监控/告警、容量压测、回滚和应急操作 | SRE、业务、测试 | 达标和风险签收 |
| 运营 | badcase 归因、数据漂移、成本指标和版本复盘 | 运营、研发 | 可归因的持续改进 |

不要声称一个岗位完成全部团队工作；说明个人负责/参与/协作边界。面试需要时使用 STAR 并补充 Why、Trade-off、Failure、Validation；教学虚拟成果不得冒充真实简历经历。

## 5. 关键工程失败链路

- **依赖/网络失败**：超时预算、重试资格、次数、退避、熔断、最终错误语义；未知结果不能直接说成功。
- **写操作**：先授权与确认；请求幂等键、重放/重复提交检测；执行中断后按业务系统状态核实，必要时补偿或人工接管。超时不自动等价于失败，也不等价于成功。
- **业务数据与缓存**：真源、敏感字段、TTL/版本、读写一致性、失效事件、权限重新校验，防止“查到旧信息却办理新业务”。
- **Agent/RAG**：工具或槽位不合法、幻觉、越权检索、提示注入、版本错引、低置信或循环；说明每种失败由哪个节点检测、如何回退或拒答。
- **模型与运维**：吞吐瓶颈、上下文截断、输出格式异常、灰度回退、API 限流和尾延迟；归属负责组件和可观测信号。

`BLOCKER`（越权、不可恢复数据破坏、重大写入错误、关键 SLO 失效）必须修复或缩小上线范围；可监控且经签收的局限列 `LIMITATION`；无当前收益的改动进 `ROADMAP`。

## 6. 数字与容量约束必须复算

定义统计口径、样本、窗口与基线。P95 ≠ 均值，峰值 ≠ 日均，模型调用次数 ≠ 用户会话轮次，Recall@k ≠ 生成正确率。容量示例**纯模拟**：6000 员工 × 30% DAU × 3 轮/日 = 5400 轮/日，全天平均 5400/86400 = 0.0625 轮/s。若**假设**峰值为日均的 5 倍，则约 0.3125 轮/s；若每轮平均 3 次模型请求，峰值约 0.9375 请求/s。并发须再考虑响应时间、排队和突发流量，不能据此认定 GPU 可承载。核对 prefill/decode 差异、KV cache、CPU/网络、GPU 显存、数据源限流与尾延迟；没有实测不能把估算写成上线能力。

分清目标阈值、离线测试、试点观察和正式线上测量；模拟提升需标明假设，因果改善需有对照或合理排除混杂因素的证据。

## 7. Demo、试点与生产的差异

- **Demo** 只证明核心链路可能可行，常缺权限、监控、异常恢复，不宣称“生产就绪”。
- **试点** 限定用户和数据，需身份/权限、受控写操作、日志、回退路径与评测。
- **生产** 需端到端正确性、稳定性和峰值性能、安全与隔离、接口兼容、故障恢复、灰度/回滚、值班和验收责任，未通过硬闸门不得声称已上线。

验收样例应注明版本、数据范围、回归样本、权限/安全用例、P95 与错误率、故障注入、监控、人工接管和回滚演练。

## 8. 局部优化与演进纪律

收到“只改模块 X”时，冻结 `CURRENT` 的其他部分，从变更点沿接口、部署/资源、权限、数据与状态、成本、故障路径、责任和成果指标检查**影响闭包**；只同步修复确实失效的字段、契约、叙述和测试，未受影响的选择不动。建议变更使用 `ChangeProposal{原因,范围,依赖影响,资源/兼容,验证,回滚,触发条件}`；只有用户授权改变基线才将提案转为 CURRENT。若多项核心约束根本冲突、局部修补仍不达标，应说明必要的整体重设计、可复用资产与迁移风险，而不是机械坚持少改。错误事实需明确纠正，而非悄悄重写。

## 9. 生产缓存的示范性决策路径（非默认全技术栈）

针对既有 LangGraph + FastAPI + Redis：先分清 workflow checkpoint 与业务数据缓存；优先缓存稳定、允许短时陈旧的**读结果**，避免缓存敏感写结果/确认卡片/强实时库存和权限决定；按租户、主体/权限版本、工具/对象、规范化查询参数设计 Key；TTL 从业务新鲜度目标和更新频率决定，必要时抖动和失效通知；业务写后删 Key，失败或不可确认时走真源；权限仍由每次真实业务读写链路校验。处理热点、击穿和隔离并用命中率、旧值率、DB QPS、P95、安全越权用例回归。只有现有方案确实无法满足目标时才增加多级缓存、事件总线或改存储。
