# lr 展示页调研与改版建议

调研日期：2026-10-21。对照版本：公开 v1.1.5，提交 `484c33e`。交付范围：同行展示调研、现有页面诊断与可执行改版规格。

后续实施已按用户的新要求改用自行设计的全新排队案例，不复用原有主题素材。下文保留当时的调研判断；当前交付见[新案例](../../examples/queue-lab/README.md)与[来源说明](../presentation.md)。

建议将演示区组织为**两条真实使用过程：用图文建立理解，以及通过讨论改进方案**。首页用清晰的代表画面或短录屏吸引阅读，案例页解释过程与价值，完整共享会话和长图承担深入阅读与复核。

## 1. 调研范围与证据

使用 Exa 按技能教学、可视化插件、应用演示和 GitHub 媒体支持四个方向检索，发起 6 次查询，获得 33 条候选结果，按 URL 去重后为 31 条。进一步读取 11 个一手页面，并用浏览器检查其中四个同行项目及我们自己的桌面、手机展示。

这是一项展示设计调研，没有安装或测试同行插件，也没有测量页面转化率。下面区分作者公开页面中可直接观察的做法和对 lr 的设计建议。浏览器记录见 [showcase-observations.json](showcase-observations.json)。

这些样本的共同启发是：**有明确用途的演示更容易解释产品价值**。这属于基于页面结构的设计判断，不是“这些页面效果已被实验证明更好”。

GitHub 官方将 README 的职责概括为说明用途、价值与开始方式，较长文档可以另行承载。[README 文档](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes)也支持把首页和深入资料分开组织。视频可以用于仓库 Markdown 演示，但实现时要使用实际支持的附件方式并实测渲染，不能假定任意 HTML 播放器都会保留。[GitHub 视频支持说明](https://github.blog/changelog/2021-05-13-video-uploads-now-generally-available/)、[媒体附件文档](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/attaching-files)。

## 3. 我们当前展示为什么不够好

### 图片缩放使关键内容难读

当前主图是 `1440 × 1100` 的整页截图。在本次浏览器检查中，桌面 1440 像素视口里的实际展示宽度为 838 像素；手机 390 像素视口中为 324 像素，即原宽的 **22.5%**。图中文字与界面一起缩小，侧栏、登录区域和留白却继续占用画面。

这能解释用户为何看得到“这里有 ChatGPT 页面”，却很难直接读懂知识地图及相关说明。观测截图：[桌面](assets/lr-desktop.png)、[手机](assets/lr-mobile.png)。

### 一段静态回答尚未呈现完整使用体验

现有共享案例包含一次提问和一次回答。它可以展示图文、公式与图表的实际呈现，但没有后续追问、参数调整或方案修订过程。因此，首页的观众很难直接看到 lr 如何帮助持续理解与讨论。

### 展示的重点需要落到 lr 的作用

图表由宿主渲染，单独一张漂亮图不能充分说明 lr 在理解和分析方面的价值。案例应让读者看到图与文字怎样互相解释：例如知识地图怎样引出模块职责，注意力矩阵怎样对应 Q/K/V 的计算，工程限制怎样从公式中推出来。

方案讨论还需要展示另一类变化：用户修正重点后，哪些依赖随之调整，哪些约束继续成立，以及当前方案为什么值得继续讨论。

### 长图和说明的阅读目的需要更清晰

`1440 × 29467` 的完整长图有存档价值，但缺乏导航和可选择文字，作为主要体验成本很高。当前标题 `A real ChatGPT conversation` 强调了真实性，尚未说明这条会话为什么值得看。详情里的来源和限制说明可以保留在明确的复核入口，首页优先解释用户能获得什么。

## 4. 推荐方案与取舍

| 方案 | 能解决的问题 | 仍需承担的成本 | 判断 |
|---|---|---|---|
| 只优化截图裁剪 | 提高代表画面的清晰度 | 静态图仍难展示连续讨论和变化 | 作为素材改进的一部分 |
| README 短演示＋按场景组织的案例页＋完整来源 | 同时展示图文结合、使用过程和方案修订；沿用现有 GitHub 分发 | 需要整理两条案例、录制短片并检查手机阅读 | **当前优先采用** |
| 独立展示站 | 可提供更宽的观看区域、视频章节、案例切换与逐轮阅读 | 增加前端、托管和持续维护；真实素材仍需先准备好 | 案例成熟后再决定是否投入 |

保留已经完善的五点用途说明，改版集中在演示区、媒体素材和案例阅读路径。展示层用静态内容、真实录屏与转录即可继续保持技能本身的轻量结构。

## 5. 演示区应该长什么样

建议标题：**看 lr 如何把知识与想法讲清楚**；英文可用 **See lr connect the ideas**。每个案例只承担一个主要任务。

| 层次 | 用户看到的内容 |
|---|---|
| 一句话定位 | 图文结合地理解复杂知识，持续讨论并改进完整方案。 |
| 主要演示 | 一段建议长度 30–45 秒的真实页面录屏，或可读的代表画面，配一句具体任务。时长是制作目标，非调研发现的行业标准。 |
| 两类案例入口 | “理解一个复杂主题”“把一个想法讨论成方案”，均说明输入和关键变化。 |
| 精选过程 | 按顺序呈现关键提问、必要回答和对应图表，附一句解释本步为何有用。 |
| 继续体验 | 复制提问、查看完整案例、打开原始共享会话、了解使用条件。 |
| 深入复核 | 完整长图、完整转录、宿主与版本信息、来源及测试记录。 |

### 案例一：从知识地图走到机制理解

素材使用现有 Transformer 真实共享页。主要画面必须同时包含一段机制解释及其对应的图、公式或图表，避免成为孤立的图集。

建议的阅读回放脚本：

1. 显示原始问题与回答主题，交代这次希望理解什么。
2. 看知识地图，说明主要模块为什么要先放在同一条信息流中。
3. 转到 Q/K/V 和注意力矩阵，让解释与数值含义同时可见。
4. 看复杂度曲线及其统计口径，展示原理怎样连接工程代价。
5. 给出完整案例和原会话入口。

现有材料适合标注为“真实会话阅读回放”。如果只是滚动历史页面，就如实说明剪辑方式；实际没有发生的追问、生成过程或控件操作不加入演示叙事。

### 案例二：从完整初案走到更合适的方案

展示三个关键时刻：

| 时刻 | 应让观众看见的变化 |
|---|---|
| 完整初案 | AI 区分“想减少操作负担”的目标与“新建 Agent 框架”的设想，给出可讨论的端到端方案。 |
| 用户纠偏 | 用户强调重复填字段，方案转向字段复用，同时保留已有工具、权限、团队和期限。 |
| 检查新提议 | 面对不可靠的身份简化建议，解释约束冲突、可用替代和当前统一方案。 |

这三个时刻已有[真实 CLI 对话记录](../../examples/planning.md)，可先制作可选择文字、逐轮展开的阅读案例并标清宿主。若要把它做成完整 ChatGPT 视觉演示，需要补充对应的真实 ChatGPT 多轮会话或录屏。现有原生共享页只有一问一答，不能承担这项证明。

## 6. 媒体与页面的制作要求

1. **主体内容可读。** 对原生截图选择连续、相关的区域，减少无关侧栏和留白；保留足够界面线索与来源入口。手机上的提问、说明和转录使用正常网页文字，关键图可点开查看原尺寸。必要时另捕获真实的移动端布局。
2. **先展示实际变化。** 有动态价值时录制真实操作或变化；仅讲述文字时使用精选转录即可。视频保留播放控制和静态封面。GIF 可作为 GitHub 的兼容选项，需实测体积与清晰度。
3. **页面说明与原生画面各有职责。** 独立案例页可以重排真实转录并增加阅读导航，明确它是精选转录；原生界面效果通过截图、录屏和共享页查看。实现不依赖把 ChatGPT 页面嵌入 iframe。
4. **记录能确认的来源。** 后续正式示例尽量记录明确选择 lr 的状态、宿主、版本及输入。现有共享页没有暴露原始模型与技能版本，继续标明这一点，不能仅凭 `lr` 字样声称已独立验证激活或增益。
5. **素材可靠保存。** 自有演示与封面随仓库或稳定的发布资源保存，保留原始记录。Mr. Ranedeer 的外链图本次没有加载出来，说明不能只凭历史图片链接假定长期可读。

## 7. 执行顺序与验收目标

1. 选定两条案例及各自要展示的关键变化，写好首屏的一句话和每步说明。
2. 用现有 Transformer 素材制作可读裁剪图和真实阅读回放；用已有三轮记录整理方案案例。把需要补充的 ChatGPT 多轮素材单独列明。
3. 重组 README 的演示区，并完善案例页的逐步阅读、来源和继续使用入口。
4. 在桌面和 390 像素手机视口实测：核心价值无需放大截图即可读懂；所有媒体、完整会话及使用链接可打开；录屏叙事与实际来源一致。
5. 再由几位首次接触项目的读者试读，观察他们能否解释 lr 的两种主要用法、找到完整案例并知道如何开始。此项是建议的后续验证，目前没有完成用户可用性测试。

优先把两条案例做清楚，再评估独立展示站的必要收益。原始会话、完整长图和历史测试资料继续通过清晰入口提供，首页则承担让人看懂和愿意继续体验的任务。
